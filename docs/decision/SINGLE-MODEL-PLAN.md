# 单模型方案（供开发者评审）

> 2026-11-01 · 针对「三个模型算法不同、没有统一契约、不能保证输出可出牌」与「卡顿依旧严重」

## 一、先说结论

1. **现在没有任何一个模型在决定出牌。** `engine.js:4149` 的注释是「★ 模型先验融合已停用：模型不再以概率改写动作分数（接管权交予冠军策略）」，下一行 `:4152` 的 `miniPredict` 调用被整行注释掉。真正出牌的是规则分 + Utility 账本 + 冠军策略提权。
2. **所以「三个模型的结果是不是合法出牌」这个问题，当前不成立** —— 它们不产生出牌，只在旁路记录。但这也正是问题：模型花了半年代码，没有一处在链路上。
3. **卡顿大概率不是模型推理造成的。** 模型既然不参与出牌，就不该是每回合的主要开销。真正要量的是：影子推理（`engine.js:4919-4924`，开关 `cfg('policyModelV3Shadow', true)` 默认开，每次决策跑一次 v3 前向）、特征提取、Utility 账本、上报序列化。

## 二、现存模型清单（代码实测）

| 模型 | 体积 | 输出 | 是否在决策链上 |
|---|---|---|---|
| 端上 MLP `weights.js` / `defaultWeights.js` | 69 KB | 134→128→64→6，标签是 `A/B/C/D/E/F` | **否**，`engine.js:4149` 已停用 |
| slot17 学生 v3 `client_policy_model_v3.js` | 51 KB | 114→32→17，输出 17 个牌种槽位 | **仅影子**，`engine.js:4924` |
| slot17 v2 `client_policy_model_v2.js` | 7.2 MB / 193,016 行 | m2cgen 导出，同样是 17 类 | **应该没有**，但 `policyModelV2.js:33` 仍在 `import()` 它 |
| 规则层 `ruleGate.js` | — | 规则 + 「模型兜底，先 shadow 记录、默认不改分」 | 是（注释 L9） |

三个模型输出三类东西：6 个抽象字母、17 个牌种、17 个牌种。**没有一个是「对具体动作打分」。** 这就是「不能保证能出牌」的根因：分类模型的输出要先翻译成动作，翻译那一步没有契约，也没有合法性约束。

顺带一个必须修的脏点：`client_policy_model_v2.js` 已经从打包里排除，但 `policyModelV2.js:33` 还在动态 import 它，运行时会走到一个 404 分支。文件删了、引用没删，这类残留会让人误判「模型还在跑」。

## 三、方案：一个模型 + 只对合法动作打分

### 3.1 选哪个

**选 slot17 v3（114→32→17，51 KB）。**

- 它是三者里唯一输出**具体牌种**的，牌种能一一映射到真实出牌；`A/B/C/D/E/F` 六个字母无法映射，留着也接不进链路。
- 51 KB，冷启动解析耗时可忽略；7.2 MB 那个不管用不用都该删。
- 已有影子接线、已有适配层，改造成本最低。

### 3.2 契约（这是「标准化权益」该落的地方）

模型不生产动作，只给动作排序。每次决策：

```
candidates = engine.enumerateLegalActions(state)   // 引擎枚举，唯一真源
if (candidates.length === 0) → 走规则兜底（过牌/结束回合）
scores = model.score(candidates, features)         // 长度必须 === candidates.length
action = argmax(scores) 中规则允许者
```

三条硬约束：

1. 模型**看不到**非法动作，输出长度与候选数不一致就整批丢弃并回退规则。
2. 模型拿不到「新建一个动作」的能力，只能排序已有候选。
3. 每次决策记录 `{candidates, scores, chosen, fallback}`，可直接从上报里看出模型有没有越权。

这样合法性是**构造保证**，不依赖模型学得好不好 —— 这也是回答「能不能保证」的唯一诚实答案：靠 mask，不靠模型。

### 3.3 目标动作空间

v3 的 17 类是牌种，同一牌种可能对应多个目标（杀谁、拆谁）。短期：

- 牌种由模型定；
- 目标由现有规则选（`cardTarget` 那条链已经成熟）；
- 等数据够再训「牌种 × 目标」的联合头。

不要在这一步引入第二个模型。一个问题一个模型。

## 四、卡顿：先量，再减

前一轮（4.4.3）的结论是「拿到设备侧证据前不再盲改决策路径」。这个原则继续用，但可以先做三件不需要设备的事：

1. **关影子**：`engine.js:4919-4924` 的 `policyModelV3.shadow` 每次决策跑一次前向 + 拼一致性摘要，还进上报队列。单模型方案落地后影子就没有存在意义，直接删。这一条最可能直接改善卡顿，而且不改变任何出牌结果，风险为零。
2. **删死引用**：`policyModelV2.js` 的 import，以及 7.2 MB 文件本体。
3. **相位计时**：在枚举 / 特征 / 打分 / 序列化四个点各加一个 `performance.now()`，随现有 `[DJSC]` 埋点上报。手机端只要能拿到一次完整对局的相位数据，就能定位到底是哪一段。

预算建议（单回合）：枚举 < 5 ms，特征 < 3 ms，打分 < 1 ms，上报序列化放空闲时段。超了就按相位砍，不猜。

## 五、分阶段

| 阶段 | 动作 | 验收 |
|---|---|---|
| P0 | 删 v2 引用与 7.2 MB 文件；关影子推理 | 包体积下降；决策结果逐局对比与改动前一致 |
| P1 | 接 v3：只对合法候选打分，异常回退规则 | 1000 局离线回放，非法动作 0 次；Top-1 不低于规则基线 |
| P2 | 用真实上报数据重训 v3（目标：牌种 × 目标） | 同口径 Top-1 超过规则基线 3 个点 |
| P3 | 拿手机相位数据做降级策略 | 单回合决策 < 10 ms |

P0 和 P1 必须能单独回滚，各自一个开关。

## 六、风险

- **v3 是 114 维，端上特征是 134 维。** 要用现成的 `dimensionAdapter` 映射回 KEEP 索引，映射错了不会报错，只会静默变差。P1 必须加一条「映射后特征指纹」日志。
- **规则基线很强。** 模型接进来如果打不过规则，就该退回规则，别为了「有模型」而硬上。P2 的 3 个点是及格线，不是目标。
- **收不上数据就没有 P2。** 4.4.x 占比目前只有 5.3%（11-01），样本量不够训联合头，先把 P0/P1 做干净。
