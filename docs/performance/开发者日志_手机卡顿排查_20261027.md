# 开发者日志 · 手机端卡顿排查（2026-10-27，4.4.2）

## 症状

- 手机端进入对局直接卡死；
- 摸完牌之后明显卡顿。

桌面复现与手机差异大，且仓库文档里「真实双客户端联机、移动端性能」一直标注为**未验收**，
因此本次先做代码路径排查，再补可测量的观测手段。

## 排查路径（按代码调用链，不靠猜）

1. **启动链**：`extension.js` 顶层 import → `mountPanels` / `installModelUpdate` /
   `installPolicyModelUpdate` / `policyModelV3` → `content()` → `installScoreEngine()`
   （`score/index.js`）→ `installHooks()`（`score/decision/engine/engine.js:3312`）→
   `startSettleWatch()`（1500ms 结算轮询）→ 44 个模块 `Promise.allSettled` 挂载。
2. **决策链**：`Player.prototype.chooseToUse` 被 `score/decision/override/use.js` 包装 →
   `bestAction()` → `bestActionCore()`：战略动作对账 → 关系指纹 → 状态指纹 →
   100ms 决策缓存 → 非本机 AI 1.5s 单玩家节流 → 9 个相位
   （preflight/context/targets/candidates/planner/model/observability/guard/telemetry）→
   决策事务随返回值带出。
3. **存储链**：训练样本 IndexedDB（`djsc_ai_db`）、对局日志 IndexedDB
   （`wumingai-journal-v1`）、`localStorage` 兜底与配额守卫。

## 结论

### 排除

- `score/model/net/client_policy_model_v2.js`（6.9MB，17 槽位模型）**全仓库无 import**，
  `policyModelV2.js` 也没有被业务模块引用 —— 它不是卡顿原因；
- `client_policy_model_v3.js`（约 50KB）走空闲期加载，telemetry 相位未就绪时直接跳过；
- 没有后台 `setInterval` 风暴：结算 1500ms、面板/战报 1000ms 等定时器只在弹窗打开或
  自动托管时活跃；
- 开局同步 `JSON.parse` 的体量受控（战报归档 ≤10 局、单局 dLog ≤5、playerLogs ≤20）。

### 进游戏卡死的嫌疑（已修一处）

`score/foundation/storage/journalStorage.js` 用**模块顶层 `await`** 等待 IndexedDB 打开
（3s 超时）。该文件被 `gameLogStore.js` 静态 import，而 `gameLogStore.js` 又被打牌引擎
`engine.js` 静态 import —— 即它是扩展启动 import 链的一环，手机慢盘上最多阻塞启动 3 秒。

### 摸牌后卡顿的主因（已修两处）

一次决策里，全量状态指纹（`stateKey()` → `makeStateKey()`：遍历自己每张手牌的名字/花色/
点数/属性、所有存活玩家的手牌数/血量/装备/判定区、事件窗口、牌堆桶）被**算了三遍**：

1. `checkStateChanged()` 算一遍（用于事件驱动缓存失效）；
2. `_decisionStateKey` 又算一遍；
3. `multiTurnCached()` 再算一遍（多回合预测的 1.2s 节流键）。

在 8 人局、手牌多、宿主 getter 慢的手机上，这一项是每次决策里最确定、可省的同步开销。

## 改动

| 文件 | 位置 | 改动 |
| --- | --- | --- |
| `score/foundation/storage/cache.js` | 240-242 | 新增 `lastStateKey()`，返回 `checkStateChanged()` 刚算出的 `_lastStateKey` |
| `score/decision/engine/engine.js` | 6946-6948 | `_decisionStateKey = lastStateKey() + '::REL=' + _currentRelationKey`，不再重复 `stateKey()` |
| `score/decision/engine/engine.js` | 5650 | `multiTurnCached()` 的节流键改用 `lastStateKey()` |
| `score/foundation/storage/journalStorage.js` | 20-22 | 顶层 `await` → `void` 非阻塞启动；`write()` 未就绪返回 false，调用方回退 `localStorage` |

语义不变：`checkStateChanged()` 与复用点之间没有任何状态写入，两次取值必然相同；
`lastStateKey()` 若未初始化返回空串，与旧行为只在冷启动首帧不同（缓存键更短，仍安全）。

## 手机上如何量

决策面板已展示最近一次「决策耗时」与「热相位」排行（`panel.js` 读取
`_finalResult.decisionMs` / `phaseMs`）。卡顿复现后打开面板记录两个数字：
总耗时 ms 与最热相位 ms。若总耗时仍 >1s，下一步按相位预算做手机降级
（跳过 observability / 缩减 candidates 与 planner 深度），先用实测数字定预算，
不拿桌面速度当手机保证。

## 4.4.3 诊断版（2026-10-27）

4.4.2 修复发布后手机端仍报「一加载模型直接卡死」。在拿到设备侧证据前不再盲改决策路径，改为「先可观测、再减负」：

- 新增 `score/foundation/diag/bootTrace.js`：`bootMark(name)` 在关键步骤打印 `[DJSC] 名称 t=毫秒`（相对扩展模块开始执行），轨迹留最近 160 条；`window.__DJSC.perfReport()` 汇总轨迹、perf 统计、权重元信息、决策次数。
- 埋点覆盖：扩展入口 → 面板挂载 → 热更检查 → content 钩子 → 引擎安装 → installHooks 各步 → 权重 / v5 / v3 载入 → 首次 bestAction。
- 打包排除 `score/model/net/client_policy_model_v2.js`（≈6.9MB 死文件，全仓库无 import）。
- 定位方法（手机端）：复现卡死后打开无名杀「设置 → 其他 → 控制台」，最后一条 `[DJSC]` 即为卡住位置；或执行 `JSON.stringify(window.__DJSC.perfReport(), null, 2)`。

结论：本版只加观测与减包，不改决策逻辑；拿到最后一条 [DJSC] 埋点后再针对性优化。
