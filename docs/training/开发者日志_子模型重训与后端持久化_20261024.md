## 二、排查：训练样本恒为 0 与上传恒为 0

### 现象
客户端「对局结束样本」长期显示 0，云端上报计数同样为 0。

### 定位过程
1. 排除网络与端点：8787 接收服务正常监听，`POST /` 校验与限流均正常。
2. 排除采集接线：`engine.js` 的局末钩子 import 与调用点均存在（`engine.js:188` / `engine.js:4944`），不是历史同类「settle 死代码」问题。
3. 定位到采样门禁：`trainExport.js` 中 `trainRecordSample()` 的第一道校验是 `features.length !== FEATURE_DIM`，不匹配即静默拒收（只记 `rejected` 计数，不抛错、不弹窗、不写日志）。

### 根因
**特征维度三方不一致**：

| 位置 | 维度 |
| --- | --- |
| `features.js` `FEATURE_DIM` | 150 |
| `trainExport.js` 本地硬编码 `FEATURE_DIM` | 142 |
| 权重本体 `defaultWeights.dims` | `[142,128,64,6]` |

`trainExport.js` 声称「特征维度单一来源，与 features.js 对齐」，但实际是**本地写死的常量**，并未 import 真源。于是 150 维特征在入口被全部拒收 → 样本池为空 → `cloudIngest` 待传样本为空 → `pendingSamples: 0` → 上报返回 `skipped: 'no-new-data'`。**一个根因同时解释了「样本为 0」和「上传为 0」两个现象。**

### 为什么没被拦住
三层防御同时失效：
- `DIM_CHECK.check()` 把 142 写死在断言里，结构上自我实现，永远返回 true。
- `index.js` 的维度漂移自检比对的是 `features.FEATURE_DIM` vs `weights.IN_DIM`，覆盖不到 `trainExport.js` 的本地常量。
- 拒收分支的诊断计数只在上传时随包上报，**面板不显示**，用户看不到「被拒」这一事实。

### 现状与处置
- 最新 master（`372cc9b`）上该问题**已修复**：`trainExport.js` 改为 `import { FEATURE_DIM } from features.js`（134 维，单一来源），注释写明「4.0.24 根因修复：维度单一来源改从 features.js 导入」。
- 本地 `E:\NoNameAI\ext` 是**未完成的实验分支**，其 150 维 schema 只改了一半（`features.js` 中 `f[142] ~ f[149]` 仅有注释、无任何赋值代码，文件头仍写「Int8 · 142 维」），权重本体实测也是 142 维。
- 处置建议：本地分支回退到 142 维止血（权重本体就是 142，无需重训），待真实数据到位后再推进 150 维 schema。

### 顺带发现：9 处 130 维硬编码残留
`championStrategy.js`（3 处）、`classicRuntime.js`、`modeTraining.js`、`playerDemonstration.js`、`config.js`、`layers.js`、`verifyAll.js` 仍按 130 维判断，在 134 体系下同样失效。属跨版本共有技术债，本轮未改动。

## 三、排查：装备召回偏低（结论为统计口径错配）

### 现象
`SubModel_Policy_slot17` 的装备类召回读数为 0.53，明显偏低，疑似短板。

### 定位
复现训练切分后发现：模型类别是**两个粗槽位**（`equip:weapon` / `equip:nonweapon`），而测试集真实标签是**几十种细粒度装备名**（`equip:bagua`、`equip:zhuge`、`equip:tengjia` …）。用细粒度标签去匹配粗类下标，统计口径错配，读数失真。

### 正确口径下的真实性能
按「装备 vs 装备」重算：

- 测试集装备样本 7,264 条，识别为装备类 **6,668 条，召回 0.918**
- 误判 596 条，主要去向为 `other`（201 条）、`card:wuzhong`（159 条）、`card:jiu`（123 条）

**装备线并不存在 0.53 的短板**，模型性能优于此前认知。残余可优化空间仅限「误判到 other」的 201 例，收益有限。本轮未因此改动模型。

## 六、8787 接收端 SQLite 持久化改造

### 6.1 背景

线上真实部署并非仓库 `backend/server.py`，而是分片式版本（部署机上的独立工作目录）：

```
<部署工作目录>/
  ├─ server_sharded.py            8787  分片式接收（数据落 E:\NoNameAI）
  ├─ Cloud_Inference_Server_v3.py  8000  严格 142 维 Hybrid_Router
  └─ Monitor_142_Data.py           监控
```

改造前的问题：
- 去重哈希、请求回执、shadow 游标**全在进程内存**，重启即丢，重启后重复样本会被当作新样本重新入库。
- 每次落盘需**全量重写所有分片 JSON** 并在内存重建全部样本哈希。

### 6.2 改造内容

新增 `dedup.sqlite`（Python 标准库 `sqlite3`，无第三方依赖），三张表：

| 表 | 内容 | 作用 |
| --- | --- | --- |
| `sample_hashes` | 样本 sha256（主键） | 样本级去重，重启不丢 |
| `request_receipts` | 请求哈希 → 回执 | 请求级幂等，进程重启后仍可返回原回执 |
| `shadow_ids` | shadow 决策 ID | shadow 采样去重游标持久化 |

设计取舍：
- **样本本体仍走分片 JSON**，不迁入 SQLite——避免 20 万级存量样本迁移风险，改动面最小，行为与改造前完全等价。
- 启动时从分片加载并 `INSERT OR IGNORE` 入库（幂等，重复执行安全）。
- 样本哈希判定改走 SQLite 查询，样本本体落盘逻辑保持不变。

### 6.3 验证

| 验证项 | 结果 |
| --- | --- |
| 隔离单测（3 条样本：入库 / 存在性判定 / 请求去重 / 回执读写 / shadow 去重） | 全部通过 |
| 重启持久性单测（进程 B 重启后哈希仍在） | 通过 |
| 线上端到端（`GET /`、空样本校验、非法样本 400、限流、样本级去重、请求级去重） | 全部通过 |
| 真实重启（杀进程 → 重启 → 首分片样本哈希在库命中） | 通过，确认不丢索引 |
| SQLite `PRAGMA integrity_check` | ok |

### 6.4 遗留与注意事项

- **测试数据已清理**：`sample_hashes` 已还原至改造前基线 222,204 条，`request_receipts` 清空，测试写入的小时归档文件已删除。
- **进程托管**：改造版服务需由**用户的计划任务或独立会话**托管（`WumingAI-DataServer` 计划任务在用户登录时触发 `E:\NoNameAI\start_server_hidden.ps1`）。受控执行环境中的后台进程会随会话回收而终止，不能作为长期托管方式。
- **现有计划任务指向的是旧单文件 `server.py`**，不是分片版 `server_sharded.py`。是否切换需单独决策，本次未改动。
