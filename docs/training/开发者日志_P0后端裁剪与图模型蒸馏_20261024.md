### 2.2 图结构的来源与防泄露设计

**必须先说清一个前提**：原始样本是**单视角的 130 维标量特征**，并不存在「每个玩家的血量 / 手牌 / 装备明细」——`m` 里只有 `actorId` / `target` / `player` / `identity` 等标识与统计增量，没有逐玩家的牌堆状态表。因此「节点 = 己方 / 队友 / 敌方，特征 = 血量 / 手牌 / 装备」只能按**特征语义段**反解重构，不能凭空还原真实牌局图。

重构方案（4 节点 / 图）：

| 节点 | 语义 | 取用的原始特征索引（全部落在 `f[0:32] ∪ f[48:130]`） |
|---|---|---|
| 0 | self（己方） | 血量 `f8,f9,f10,f11`；手牌 `f0,f1,f2,f3,f4,f5`；装备 `f24,f25,f26,f27`；身份 `f12..f15`；存活 `f16`；对敌均差 `f65` |
| 1 | ally（队友） | 数量/濒死 `f18,f19`；HP 占比 `f70`；手牌占比 `f71`；集火/保护 `f112,f113`；对敌均差 `f64,f65,f66`；阵营/分差 `f67,f68` |
| 2 | enemy（敌方） | 数量/濒死 `f17,f20`；装备（诸葛/藤甲）`f21,f22`；占比 `f70,f71`；均差 `f64,f65,f66`；`f67,f68`；牌堆 `f88..f91` |
| 3 | target（动作目标） | 手牌概率 `f80,f81,f82,f83,f84`；距离 `f85`；压力 `f86`；攻击/爆发技能 `f100,f101`；仇恨 `f103`；防御技能 `f129` |

**防泄露是硬约束**：`f32..f47` 是动作泄露维（`f32` 直接编码所出的牌种，`f36/f39` 编码攻击/杀），P2 训练脚本正是因此把 `f32:48` 整段排除。若图节点引用该段，GNN 就是在读答案，与 LGBM 基线不可比。因此**图节点特征完全不含 `f32..f47`**，与 114 维 KEEP 同源同口径。

统一节点维度 **20**（不足补零），节点总数 **4/图**；边采用全连接有向图 **16 条/图**（含 4 条自环），边特征维度 **4**：`[is_ally, is_enemy, is_self_loop, focus_flag]`，`focus_flag` 取 `f87`（集火目标，落在安全区内，与泄露维 `f47` 语义相同但取值源不同）。

## 三、模型训练：FT-Transformer vs GAT（同口径对比）

### 3.1 统一口径

所有模型共用同一份 194,338 条纯真人已结算样本、同一套 114 维特征、同一 17 类标签、同一 session 级 8:2 切分、同一份测试集 39,240 条，评估口径与 P2 一致（按概率降序取 Top-k，检查真值是否落入）。

### 3.2 结果

| 模型 | Top-1 | Top-5 | 备注 |
|---|---|---|---|
| LGBM（`SubModel_Policy_slot17` 同超参复现） | **0.6440** | **0.9717** | 本口径基线 |
| FT-Transformer（Attention） | **0.6404** | **0.9695** | 最佳轮次（d64/L2/ff128，20 epoch） |
| GAT（GNN） | **0.4366** | **0.8320** | 4 节点图重构，结构信息量受限 |
| **LGBM + FT 集成（Teacher）** | **0.6468** | **0.9723** | 概率平均 0.5/0.5 |
| 目标（用户给定基线） | 0.6504 | — | 见 3.4 口径溯源 |

### 3.2.1 FT-Transformer 的三轮尝试（诚实记录）

FT-Transformer 一共训了三轮，**最终结论是它在本任务上追平但未超越端上受限版 LGBM**：

| 轮次 | 架构 | 正则 | epoch | Top-1 | 结论 |
|---|---|---|---|---|---|
| v1 | d_token 64 / 2 层 / d_ff 128 | dropout 0.1 | 20 | **0.6404** | 最佳，接近 LGBM 0.6440 |
| v2 | d_token 96 / 3 层 / d_ff 192 | feat_drop 0.05 | 设定 60，实际跑至 58 轮（后台进程被回收） | 0.5683（最佳轮次远低于 v1） | **过拟合**：train loss 0.88 但验证 Top-1 长期卡在 0.57 |
| v3 | d_token 64 / 2 层 / d_ff 128 | dropout 0.15 + feat_drop 0.03 + label_smoothing 0.05 + wd 1e-3 | 30 | 0.6286 | 正则过重，反而低于 v1 |

结论：**该架构在本数据上的上限约 0.64**，与 LGBM 0.6440 基本同水平；放大模型或堆正则都没有收益。

### 3.2.2 集成 Teacher

LGBM 与 FT-Transformer 的错误相关性中等，把两者概率按 0.5/0.5 平均后得到 **Top-1 0.6468 / Top-5 0.9723**，高于任一单模型，作为蒸馏 Teacher。

### 3.3 为什么 GAT 明显落后

不是实现问题，是**信息瓶颈**：

- FT-Transformer 直接吃 114 维全特征；
- 本轮图重构只能把其中 **57 维有效语义**（self 20 + ally 11 + enemy 15 + target 11）装进 4 个 20 维节点，其余 57 维全部丢失；且这 57 维本身就是聚合统计（敌均手牌、友方占比等），并**没有额外的结构化关系**让 GAT 的注意力去利用。

换言之：这里的「图」是**从标量特征反解出来的角色图**，GAT 的结构归纳偏置在这里没有用武之地。这条结论对本项目是重要的负向结论——**不要为了赶时髦把 GNN 引入决策链路**，除非上游真的开始上报逐玩家状态。

### 3.4 关于「LGBM 65.04%」的口径溯源（重要）

用户给出的基线 65.04% 在本轮口径下**未能复现**（本轮同口径复现为 64.40%，与仓库既有 slot17 权重的记录值完全一致）。追查后定位到原因：

用 `real_pool.npz`（99,375 条 / 130 维 / 带 sessionId）做对照实验：

| 特征口径 | Top-1 | Top-5 |
|---|---|---|
| 130 维全特征 | **0.8190** | **1.0000** |
| 114 维 KEEP（去泄露维） | 0.5878 | 0.9240 |

**130 维全特征能到 81.9% / Top-5 满分**，正是因为 `f32..f47` 泄露了动作本身——模型可以直接读答案。所以 65.04% 极可能来自**含泄露维或更宽松口径的旧基线**，而不是「无泄露 114 维 + session 切分」下的可比数字。

因此本轮的对照基准取**同口径复现值 64.40%**，并在汇报中同时给出绝对值 65.04% 的达成情况，不混淆两套口径。

## 四、蒸馏与热更

### 4.1 Teacher 选择

| 候选 | Top-1 | Top-5 |
|---|---|---|
| LGBM | 0.6440 | 0.9717 |
| FT-Transformer | 0.6404 | 0.9695 |

Teacher 在**训练集**上打软标签（温度 T），与硬标签按 `loss = (1-α)·CE + α·KL(T²)` 混合蒸馏。

### 4.2 Student 架构与训练

- 架构固定为指令要求的 **114 → 32 → 17**（`Linear(114,32) + ReLU + Linear(32,17)`），17 类输出；
- 权重 4,250 个参数，float64 导出；
- 蒸馏超参经 10 组网格搜索定稿：**α = 0.7，T = 1.5，epoch = 160**（OneCycle，batch 1024，AdamW lr 2e-3 / wd 1e-4）。

| 轮次 | α | T | epoch | Student Top-1 | Top-5 |
|---|---|---|---|---|---|
| 默认 | 0.7 | 2.0 | 40 | 0.6066 | 0.9578 |
| 搜索 | 0.9 | 2.0 | 40 | 0.6044 | 0.9577 |
| 搜索 | 0.85 | 3.0 | 40 | 0.6011 | 0.9560 |
| 搜索 | 0.7 | 1.5 | 40 | 0.6092 | 0.9576 |
| 搜索 | 0.7 | 1.5 | 90 | 0.6187 | 0.9602 |
| **定稿** | **0.7** | **1.5** | **160** | **0.6228** | **0.9609** |

Student 比 Teacher 低 2.4pp，这是 32 维隐层的容量代价，属预期内。

### 4.3 导出 `client_policy_model_v3.js`

产物：`score/model/net/client_policy_model_v3.js`（**51,634 字节**，与 v2 同目录）。

- `META` 内含：17 类标签、`featureKeep`（114 个索引，与 v2 / LGBM 完全一致）、`normMin` / `normRange`（float64）、`w1/b1/w2/b2`（base64 编码的 float64）、`threshold`、`schema = slot17_student_v3`；
- 对外接口与 v2 对齐：`predictProba(features130)` / `rawScores(features130)` / `topK(features130, k)` / `selfTest()`；
- 输入为 **130 维原始特征**，内部按 `featureKeep` 取 114 维并做 min-max 归一化，与 v2 的调用方式一致（客户端无需改调用协议）；
- 权重用 base64(float64) 而非 JSON 数组：体积更小、无精度损失。

### 4.4 Python-JS 对拍（1000 条）

从测试集取 **1000 条真实样本**，以 130 维原始特征分别喂给 Python 前向与 JS 前向，逐样本比对：

| 指标 | 结果 |
|---|---|
| 样本数 | 1000 |
| **Top-1 类别一致** | **1000 / 1000 = 100.00%** |
| 最大 logits 偏差 | **0.000e+00**（bit 级相同） |
| 最大概率偏差 | 5.551e-16（softmax 最后 1 ulp） |

**SHA256**：`9ee78420c5970158427e4c919f166ab9c77bcf29fb40d5f428fcdde7698603d5`

### 4.5 对拍过程中发现并修复的一个真 bug（重要）

首轮对拍出现 **Top-1 100% 一致、但 logits 最大偏差 7.69e-02** 的矛盾现象。逐层排查后定位到：**JS 导出模板里手写的 base64 解码器 `b64ToF64` 在末组只剩 2 个有效字符时少写 1 个字节**，导致 `B1` / `B2` 两个偏置向量整体错位一字节（`W2` 因长度恰好整除而未受影响），第二层输出全错。

修复方式是按「本组剩余有效字符数」逐字节判定（`rem >= 2 / 3 / 4` 分别写 1 / 2 / 3 字节）。修复后 logits 偏差降到 **0.000e+00**。

影响面核查：仓库既有的 base64 解码（`js/update/weightBundle.js`、`score/model/weights/weights.js`）全部使用浏览器原生 `atob`，**不受此 bug 影响**；仅本次新增的手写解码器踩坑，已修复。

这一步说明：**Python-JS 对拍不是形式主义**——若只比 Top-1 类别，这个权重错位 bug 会被完全掩盖（类别排序不变，精度已废）。

### 4.6 热更接入路径（本轮未接，方案已定）

仓库既有的模型热更通道是 8787 `server_sharded.py` 的 `/update/model/manifest.json` + `/update/<pkg>.zip`，扩展端由 `js/update/weightBundle.js` 消费。v3 若要接热更，需要：

1. 把 `client_policy_model_v3.js` 打进 update zip，manifest 增加 `modelId = slot17_student_v3` 与 `releaseSeq`；
2. 扩展端新增 `policyModelV3.js` 适配器（参照 `policyModelV2.js`，把 `>= 130` 的维度兼容处理一并带上），并在 `weightBundle.js` 的校验通过后触发 v3 切换；
3. v3 默认仍走 **shadow 模式**（只记录一致性、不改候选分），达到连续达标后再切 active。

本轮按指令只交付「导出 + 对拍 + SHA256」，**未改动扩展端任何运行时行为**。
