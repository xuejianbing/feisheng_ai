# 开发者日志：v4.1.2.8-beta.4 内测包合并与发布（2026-10-24）

本文记录本轮从「多分支收敛 → 内测客户端整包」的处理过程，重点是**哪些分支合了、哪些没合、为什么**，以及安装包体积这一处实际踩到的坑。

## 一、背景

仓库远端长期存在多条并行分支，其中三条相对 `master` 尚未合并。开发者与客户评审后，**端云协同方案被否决**，因此本轮的首要任务不是"把所有分支都合掉"，而是先判定每条分支的归属，再决定合并或搁置。

## 二、分支判定

以 `origin/master` 为基准逐条核对（`git rev-list --left-right --count master...branch`）：

| 分支 | 领先 master | 判定 | 依据 |
| --- | --- | --- | --- |
| `codex/doudizhu-review-boundaries` | 2 | **合并** | 纯客户端决策逻辑修复，与端云协同无关 |
| `feature/backend-ingest-receipts` | 1 | **不重复合并** | 内容已由 PR #7 以 `5033a77` 合入 master，两点 diff 完全一致 |
| `fix/client-align-142` | 2 | **不合并** | 即端云协同方案本体，已被否决 |

### 2.1 `feature/backend-ingest-receipts` 的判定细节

初看 `git diff origin/master...origin/feature/backend-ingest-receipts` 会显示 `cloudIngest.js` 有一整块"新增 import 与接线"的差异，容易误判为未合并。**这是三点比较的假象**——三点 diff 比较的是 merge-base 到分支，而非 master 到分支。

改用两点比较 `git diff origin/master origin/feature/backend-ingest-receipts -- score/foundation/cloud/cloudIngest.js`，结果为**完全一致**；再核对 master 的提交历史，`5033a77 Add frontend ingest receipts and training diagnostics` 与分支上的 `000c777` 是同一 patch 的两个 commit hash，PR #7 走的是 `publish/ingest-receipts` 分支，内容早已进入 master。

**结论：合并它等于重复引入同一份改动，应跳过。**

### 2.2 `fix/client-align-142` 的判定依据

该分支两个提交：

- `18f7204 feat: bump formal feature dimension 134 to 142 for client contract alignment`
- `25cae88 feat: align 142 features and integrate cloud api`

改动内容：新增 `score/foundation/cloud/cloudInference.js`（271 行）、`features.js` 特征维度 134→142、`weights.js` / `defaultWeights.js` 同步改维度、`engine.js` 接入云端推理。

这就是端云协同方案的客户端侧实现。它会把扩展端正式特征维度从 **134 改为 142**，直接冲击两处既有契约：

1. 扩展端内置权重快照格式 `dims=[134,128,64,6]` 与 `weightBundle` 校验口径；
2. 线上推理服务 `Cloud_Inference_Server_v3.py` 的严格 142 维 `Hybrid_Router` —— 反向也不成立，线上 142 维与扩展端 134 维本就是两套独立体系。

方案被否决后，**本版保持 134 维契约不变**，该分支保留在远端不予合并（删除远端分支属不可逆对外动作，留待仓库所有者决定）。

## 四、安装包体积：一处实际踩到的坑

`.github/workflows/manual-package.yml` 用**白名单**方式打包，`model` 目录在白名单内：

```python
for name in ("assets", "css", "js", "logs", "model", "score", "shadow"):
```

而上一轮刚入库的 `model/submodels/` 共 **14.6 MB**（3 个 `.pkl` 合计 7.28 MB、`client_policy_model_v2.js` 7.04 MB、对拍快照 0.9 MB）。

全仓 grep 确认**扩展端代码对这批产物零引用**：

```
submodels: <无引用>
client_policy_model: <无引用>
slot17: <无引用>
Critic_WinLoss: <无引用>
```

也就是说，它们是**服务端训练产物**，留在 `model/` 会被原样打进每个客户端安装包，纯属浪费。

**处理**：迁至 `artifacts/submodels/`。`artifacts/` 不在打包白名单内，随仓库分发但不随客户端分发。同步更新 `CHANGELOG.md`、`docs/training/` 开发者日志、`tools/training/README.md` 中的路径引用，并在 `artifacts/submodels/README.md` 顶部写明迁移原因，避免后人误挪回去。

> 顺带一提：仓库原有的 `model/v5_mixup_s42.json` / `v5_mixup_s456.json` 同样未被扩展代码直接引用，但那是既有产物，本次不动。

## 五、版本号与打包校验

`manual-package.yml` 有一条硬校验：`info.json` 的 `version` 必须与 `js/config/version.js` 的 `VERSION` 完全一致，否则打包中止。

本版从 `4.1.2.8-beta.3` 升到 `4.1.2.8-beta.4`，同步更新：

- `info.json` → `"version": "4.1.2.8-beta.4"`
- `js/config/version.js` → `VERSION` / `VERSION_SEMVER` = `4.1.2.8-beta.4`，`BUILD_DATE` = `2026-10-24`
- `README.md` → 最近更新区块、版本历史表新增一行、当前版本行
- `CHANGELOG.md` → 顶部新增本条目

**未改 `info.json` 的 `author` 字段**，仍为原作者"飞升"。

本地已用与 workflow 相同的正则做前置校验：版本号格式合规、两侧一致。

## 八、后续建议

1. **远端分支收敛**：`fix/client-align-142` 若确认永久废弃，建议由仓库所有者删除，避免后续误合并——它的 `features.js` 维度改动一旦合入，会与 `djsc_weights_v3` 的 `dims=[134,128,64,6]` 直接冲突。
2. **打包白名单常态化校验**：`artifacts/` 这次是人工识别后迁走的。建议在 `manual-package.yml` 增加一步体积上限告警（如超过 N MB 打印警告），防止后续再有服务端产物误入 `model/`。
3. **版本号单一来源**：`info.json` 与 `version.js` 双写是打包脚本强制的老问题。当前靠提交前人工校验维持，可考虑改为从 `version.js` 单向生成 `info.json`。
4. **分支归并规范**：本轮遇到的 `feature/` 与 `publish/` 同内容双分支（不同 hash）会造成重复合并判断，建议约定 PR 合并后即删源分支。
